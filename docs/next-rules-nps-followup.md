## プロファイルと変更

`perf_event_paranoid=4` の環境で、こちらから起動したベンチマークの命令ポインタを
ptraceでルール・版ごとに1,200回サンプリングした。CPU 2に固定し、1〜4 msのランダムな間隔で採取。
ELFの実行セグメントのオフセットを使って各アドレスをシンボルに対応づけた。

元の版では二玉・取る一手・飛車・角の各ルールで `geometric_targets` が自己サンプルの
39〜50%を占めた。先行版ではこの処理の割合が低下し、候補手の合法性判定と
`set_cell` が目立った。二玉・取る一手・飛車・角の先行版で、`set_cell` は自己サンプルの
10〜13%を占めた。今回版では同じ4ルールで7〜8%だった。

- 幾何的な王手がなく、ピンされていない非王駒の1段移動では、段と筋の制約を元の盤面で判定する。
  打ち歩詰めの対象外である非王駒の駒打ちにも同じ判定を使う。
  王手中・ピン候補・王駒・複数段の手・打ち歩詰めの対象は作業用の盤面で判定する。
- 取る一手の疑似取りの検査では王手判定と利き先バッファを再利用する。
  取りの義務がある局面では、初段で取らない手と駒打ちを候補の組み立て前に除く。

## 再現

`c626456` のソースで `276379a` に保存された依存ロックを使用した。Rust 1.98.1、
Intel Core i7-6700、releaseのopt-level=3、codegen-units=1、LTO=fat。CPU 2に固定した
1スレッドで初期局面のperft(3)を測り、各試行は3秒以上とした。NPSは全ての手を適用して
得た葉数を経過秒で割った値で、各ルールの中央値を使った。

```sh
cp plans/next-rule-groups/perft/20261126/workspace-Cargo.lock Cargo.lock
python3 scripts/benchmark-next-rules.py prepare --output target/next-rules-nps-followup
python3 scripts/benchmark-next-rules.py run --output target/next-rules-nps-followup --cpu 2
```

同日比較では各ルール・版につき3試行を別プロセスで実行し、版の順番を試行ごとにずらした。
各プロセスでウォームアップを除外した。ホスト全体のCPU使用が1.5コアを超えた試行は
再実行した。元の版と先行版のバイナリは先行の記録にあるSHA-256と照合した。

個別の試行は `taskset -c 2 <バイナリ> <ルール名> 3 3000 1` で再現できる。
