# 安北NNUE 小型ネット計画 フェーズ0：既存データの監査結果

- 実施日: 2026-11-23
- 計画: [plans/anhoku-nnue-small-net-plan.md](../plans/anhoku-nnue-small-net-plan.md)
- 範囲: 既存のコーパスと対局記録だけを使い、CPUで集計した。学習・教師生成・GPUは使っていない。NPSの補足測定として、手元で8局だけ対局した。

## 要点

1. **HalfKAの行は、玉の位置で分けない場合に比べて約20〜30倍薄く学習されている。**
   評価時に使われる特徴を数えると、その特徴の行が訓練データに出た回数の中央値は、HalfKAでは約1.2万回だった。玉の位置で分けない射影では25万〜39万回である。
   HalfKAでは、訓練データでの出現が1,000回未満の行が評価時の特徴の17〜22%を占め、100回未満の行でも4〜8%を占める。玉で分けない射影では、どちらも1%未満だった。
2. **教師局面の分布が実戦とずれている。**
   実戦（100ms）は絶対手数の中央値53手で終わり、80手に届く対局は11%だった。
   これに対して、訓練局面の32%（モデルBのコーパス）は80手目以降にある。中盤以降の局面は、ほとんどが勝負のついた局面だった（評価値の絶対値の中央値は16〜58歩分）。
3. **局数と開始局面が少ない。**
   モデルBのコーパスは、3万局を104通りの開始局面（52の序盤×先後）から指したもの。モデルAのコーパスは13,749局・45序盤グループである。
   盤面の重複はほとんどない（88万局面中86〜88万が別の盤面）。実効標本数を制限しているのは局数のほうである。
4. **1万ノードのラベルは、実質的に深さ2前後の探索である。** 完了深さは、1が22%、2が40%、3が25%、4が12%だった。
5. **計画に書いた「NNUEはNPSが半分で損をしている」は誤りだった。**
   1局ずつ指す条件では、NNUE（L1=256、83MB）のほうが手書き評価より速い。MBPでの512局では、NNUEが24.5万NPS、手書きが18.3万NPSだった。
   以前の「17k対35k」は、21局を同時に指した条件での値である。
   したがって、小型化を勧める理由は、持ち時間あたりの速さではなく、1と3（標本効率と再現性）、それにブラウザでのサイズとメモリになる。
6. **成功したモデルAと失敗したモデルBは、教師局面の生成方法が違う。**
   - A: R4-replacementのコーパス。近最善手の一様選択、一様な合法手の摂動、256ノードと1,024ノードの自己対局を混ぜたもの
   - B: 深さ1の手書き探索からの確率的な選択だけ
   
   Step 9の結論は「AとBの差はデータの取り方の偶然」だった。しかし、生成方法そのものが原因である可能性が残っている。

## 1. 行のカバレッジ

ツールは `haitaka_learn small-net-coverage-audit`。詳細な結果は
[train=B](../r0/anhoku-small-net/phase0-coverage-train-b.json) と
[train=A](../r0/anhoku-small-net/phase0-coverage-train-a.json)。

数え方は次のとおり。各局面の両視点について、本番の特徴抽出（`r1_donor_single_active_feature_indices`）が返す行を数えた。
「玉で分けない」は、HalfKAv2^の行番号から玉の升のオフセットを除いた射影（1,863行）である。小型ネット「A+Donor」が使う入力と同じになる。
対象の行数は、HalfKAv2が150,903行（81升 × 1,863）、DonorSingleEffが1,620行。L1=256のモデルでは、この約15.3万行が83MBの大半を占める。

### 訓練データ（モデルB、88万局面）の中で

| 行の種類 | 行数 | 出現した行 | 出現した行の出現回数の中央値 | 出現100回未満の行 |
|---|---:|---:|---:|---:|
| HalfKAv2 | 150,903 | 121,377（80%） | 41 | 83,301 |
| 玉で分けない射影 | 1,863 | 1,559（84%） | 7,299 | 2 |
| DonorSingleEff | 1,620 | 1,386（86%） | 1,374 | 10 |

自玉の升（視点ごとに向きを揃えたもの）は、標本の50%が5升、80%が19升、90%が37升に分布していた。
玉が序盤の数升に留まるのではなく、広く動くので、玉ごとのブロックに入る標本が薄くなる。

### 評価データの特徴が、訓練データで何回学習されたか

評価データに現れる特徴を、その特徴の行が訓練データに何回出たかで分類した。表の値は、評価データの全特徴に占める割合である。

| 訓練 → 評価 | 行の種類 | 出現0回 | 100回未満 | 1,000回未満 | 中央値 |
|---|---|---:|---:|---:|---:|
| B訓練 → B検証 | HalfKA | 0.02% | 3.8% | 17.9% | 12,015 |
| | 玉で分けない | 0 | 0.001% | 0.08% | 391,607 |
| | Donor | 0 | 0.0002% | 2.6% | 94,706 |
| B訓練 → A訓練（独立な生成方法） | HalfKA | 0.01% | 3.6% | 18.7% | 10,642 |
| | 玉で分けない | 0 | 0 | 0.16% | 246,389 |
| A訓練 → B検証（独立な生成方法） | HalfKA | **1.1%** | **7.7%** | **21.7%** | 12,233 |
| | 玉で分けない | 0.02% | 0.07% | 0.42% | 252,738 |
| | Donor | 0.009% | 0.4% | 5.4% | 119,099 |

HalfKAの各行は256次元の重みベクトルを持つ。数十〜数百回しか更新されない行が、評価時の特徴の数%〜2割を占めている。
生成方法が違うデータへ移ると、この割合はさらに増える。
モデルAとBの成績の差、早い段階で検証損失が悪化したこと、幅512にしても強くならなかったこと。どれもこの状況と矛盾しない。
データを10倍にしても、HalfKAの中央値は約12万回で、現在の「玉で分けない」射影（25万〜39万回）にまだ届かない。

## 2. 教師局面の分布と実戦の分布

詳細は [score-ply](../r0/anhoku-small-net/phase0-score-ply.json) と [実戦](../r0/anhoku-small-net/phase0-match-games-mbp.json)。
実戦の記録は、Step 10の100ms対局512局（NNUE対手書き、MBP、1局ずつ）である。

| 手数の範囲 | B: 局面の割合 | B: 評価値の絶対値の中央値 | B: ±300以内の割合 | A: 局面の割合 | A: 中央値 |
|---|---:|---:|---:|---:|---:|
| 0〜19 | 12% | 240 | 53% | 2% | 26 |
| 20〜39 | 22% | 810 | 26% | 17% | 386 |
| 40〜79 | 34% | 1,604 | 12% | 39% | 1,400 |
| 80〜119 | 20% | 3,242 | 6% | 26% | 2,260 |
| 120〜199 | 13% | 5,788 | 3% | 16% | 2,760 |

歩は100点である。全体では、評価値の絶対値が3,000（30歩分）以上の局面がBで32%、Aで28%を占める。

実戦では、終局時の絶対手数は p05=33、p25=43、p50=53、p75=65、p95=89 だった。80手に届く対局は10.7%、120手に届く対局は0.4%しかない。
512局すべてが「合法手なし」（詰み）で終わっていた。

教師データの約3分の1は、実戦ではほとんど現れない「長く続いた、勝負のついた局面」である。
深さ1の探索で手順を決めるので、早い段階で大差がつく。その後も投了しないまま180手まで続き、そこを抽出しているためと考えられる。
勝敗を分けるのは評価値が接近した局面だが、その局面は1〜2割しかない。

## 3. 局数・開始局面・ラベルの深さ

| | モデルAのコーパス（R4-replacement） | モデルBのコーパス（strength-first v2） |
|---|---|---|
| 局数 | 13,749 | 30,000 |
| 開始局面 | 45の序盤グループ | 52の序盤 × 先後 = 104 |
| 手順の決め方 | 近最善手の一様選択 38万、一様摂動 24万、256ノード自己対局 15万、1,024ノード自己対局 10万 | 深さ1の手書き探索から確率的に選択（候補4手、余裕80点、温度40） |
| 別の盤面 | 877,988 / 880,000 | 863,005 / 880,000 |
| 1局あたりの局面 | 約64 | 約29 |

Bの生成では、詰みの評価値になった局面320,696を捨てている（候補170万局面中）。

Aのラベルは1万ノードで、完了深さは1が192,651、2が354,711、3が222,838、4が107,083、5以上が約2,700だった。
実戦（100ms）の完了深さは2.4〜3.7なので、ラベルの探索は実戦の探索とほぼ同じか、やや浅い。

## 4. NPS

| 条件 | NNUE（step10系、L1=256） | 手書き |
|---|---:|---:|
| MBP、100ms、1局ずつ、512局 | 244,642 | 182,574 |
| 手元 i7-6700、100ms、1局ずつ、8局（`step10-u768`） | 84,662 | 66,882 |

手書き評価には、両者の合法手数の差（可動性）が入っている。その計算が重いため、手書き側のほうが遅いと見られる。
1局ずつ指す本番の条件では、NNUEの持ち時間あたりの損はない。
83MBや161MBのモデルの問題は、速さではなく次の点である。
- 標本効率と再現性（1と3）
- ブラウザでのダウンロードサイズとメモリ（Step 6の1秒対局でRSSが1.85GiB）
- 複数局を同時に指す場合の速度低下（WASMで1局ずつ指す場合の速度は未測定）

## 5. 計画への反映

- 小型ネット「A+Donor」の入力は、今回監査した「玉で分けない射影」（1,863行）とDonorSingleEff（1,620行）を合わせた**3,483行**とする。L1=256なら第1層は約1.8MB（int16）。
- フェーズ2の比較に、**教師局面の選別**を加える。
  例えば、評価値の絶対値が3,000未満で100手未満の局面だけを使う、あるいは実戦の手数分布に合わせて重みを付ける。
  これらを、既存の88万局面だけで小型ネットを使って比べる。
- フェーズ3の教師生成では、手順の決定に実戦に近い探索（ノード数を固定）を使う。
  評価値の絶対値が閾値（例えば3,000）を超えた状態が続いたら、その局を打ち切る（やねうら王の `eval_limit` に当たる）。
  局数は10万局以上を目安にする。長い大差の局面が減るので、生成費用も下がる。
- 「NPSが半分」という理由は計画から削除した。

## 再現手順

```bash
cargo build --release -p haitaka_learn --features anhoku
D=../haitaka-variants-anhoku/out
./target/release/haitaka_learn small-net-coverage-audit \
  --train $D/anhoku-strength-first/step9-model-b-corpus-20260911-v1/training.bin \
  --eval  $D/anhoku-strength-first/step9-model-b-corpus-20260911-v1/validation.bin \
  --eval  $D/anhoku-reboot-r4-replacement/datasets/training.bin \
  --eval  $D/anhoku-strength-first/step12-independent-replication-20260916-v1/data/frozen-corpus-v1/training.bin \
  --output r0/anhoku-small-net/phase0-coverage-train-b.json
./target/release/haitaka_learn small-net-coverage-audit \
  --train $D/anhoku-reboot-r4-replacement/datasets/training.bin \
  --eval  $D/anhoku-strength-first/step9-model-b-corpus-20260911-v1/validation.bin \
  --output r0/anhoku-small-net/phase0-coverage-train-a.json
python3 scripts/small_net_phase0_stats.py scores <training.bin>... > r0/anhoku-small-net/phase0-score-ply.json
python3 scripts/small_net_phase0_stats.py games \
  $(find $D/anhoku-strength-first/step10-checkpoint-selection-20260914-v3-approx-100ms/matches \
      -path '*native-raw/self-play-games.jsonl') > r0/anhoku-small-net/phase0-match-games-mbp.json

cargo build --release -p haitaka_cli --features anhoku,nnue-l1-256
./target/release/haitaka_cli self-play --games 8 --threads 1 --a-eval handcrafted --b-eval nnue \
  --b-nnue <step10-u768.nnue> --movetime-ms 100 --openings <anhoku-v3のSFENだけを抜き出したファイル> \
  --opening-order random --seed 7 --max-plies 200 --report-dir <dir>
```

監査ツールの実行時間は、88万＋約190万局面で約30秒（i7-6700、1スレッド）だった。
