# 平安9×9・持ち駒不使用将棋でSFNNが弱い理由の診断

## 結論

「捕獲しても持駒が増えない」という違いは、評価入力と捕獲の評価に大きく影響する。
ただし、仮想持駒を評価器に補うだけでは棋力は回復しなかった。
本将棋用の評価器を、駒が消え、駒打ちもないルールに転用していることが有力な原因。
今回の実験から特定のニューラル層や学習要素まで原因を断定することはできない。

探索量を揃えても大敗するため、評価速度だけでは説明できない。
持ち駒不使用将棋では、全再計算による速度低下も重なる。
既定の手書き評価を維持し、仮想持駒や特徴0の変更を製品には適用しない。

## 同じ探索量での対照実験

つようら王11micro対手書き評価。数字はつようら王側の勝・敗・分。
各条件24局、12序盤の先後交換。同じルール内は全条件で同じ開始局面を使用した。

| 条件 | 本将棋 | 平安9×9 | 持ち駒不使用 |
| --- | ---: | ---: | ---: |
| 通常入力・1手100ms | 未実施 | 0–24–0 | 0–24–0 |
| 通常入力・1手4096ノード | 24–0–0 | 0–24–0 | 1–23–0 |
| 評価器だけ仮想持駒・4096ノード | 対象外 | 0–24–0 | 3–20–1 |
| 欠駒の特徴0をゼロ化・4096ノード | 対象外 | 0–23–1 | 2–22–0 |

4096は通常探索と静止探索の合計。全てのノード制限対局で、要求・消費ノード数が一致。
全216局で対局エラー・代替着手0。分は全て512手打切り。
同一の探索・合法手・終局判定で評価器を切り替えている。本将棋で勝てることを対照として確認した。

仮想持駒は捕獲履歴から復元し、**ニューラル評価の入力だけ**に追加する。
実盤の持駒は0のままで、駒打ちは生成しない。平安の金成りも元の駒種を追跡する。
これは学習分布に近づける介入だが、使えない持駒の攻撃・受けを評価器が期待する副作用がある。
したがって失敗しても「持駒の欠如は無関係」とは言えない。
平安では開始時から飛角4枚がない違いも、この介入では補っていない。

24局は原因を絞るための小規模な探索的実験。1勝と3勝の差を改善の証明に使わない。
今回の介入対戦はmicroのみ。miniは前回100局で1勝99敗だったが、同じ介入対戦は未実施。

## 入力と評価の確認

通常将棋では、取った駒の盤上特徴が消える代わりに持駒特徴が増え、物理駒数は保存される。
両対象ルールでは取った駒が盤から消え、SFNNでは欠けた駒のスロットを特徴0で埋める。
モデルにはルール種別の入力がなく、この取り捨て・駒打ちなしの局面用に再学習していない。

開始局面から相手の歩1枚を削除する静的介入を、相手の歩9枚それぞれで行った。
同じ駒を仮想持駒に入れた場合と比べると、持駒のない捕獲の評価増分が小さい。
表は評価値の平均差であり、合法な1手の評価でも、駒の真の価値の測定でもない。
削除による利き・進行度の変化も含む。手書き評価との数値スケールの直接比較には使わない。

| ルール・モデル | 歩を削除のみ | 削除＋取った側の仮想持駒 |
| --- | ---: | ---: |
| 平安micro | +45.1 | +251.8 |
| 平安mini | +61.0 | +195.9 |
| 持ち駒不使用micro | +25.0 | +235.4 |
| 持ち駒不使用mini | +45.8 | +291.6 |

前回対戦の先頭4局から12手ごとに採った35/42局面でも静的評価と合法捕獲を保存した。
負の捕獲差分だけで誤評価とは断定しない。実際に悪い捕獲も含むためである。

### 実装バグとの切り分け

- miniの50局面で、外部のやねうら王参照実装と評価値・進行度合計・バケットが完全一致。
  初期局面に加え、両ルールの捕獲後の局面を含む。
  参照側の物理金4枚制限を超える平安局面は除外し、SFENを重複排除した。
- 参照は既存検証と同じYaneuraOu `7d9743646f1006ff6d84da45d6d6160048a5a416`、
  mini構成、`FV_SCALE=24`。外部プロセスとして実行し、参照コードを組み込んでいない。
- 参照実装も欠けた物理駒に特徴0を使用する。特徴0のNN重みは非ゼロだが、
  「ゼロだから無効」と誤解して省略しているわけではない。進行度側の特徴0重みはゼロ。
- 特徴0のNN行を全てゼロにする介入でも大敗が続いた。これ単独を主要因とする証拠はない。
- 前回、micro/miniそれぞれ2,304遷移で差分更新と全再計算が一致している。
  今回はそれに独立した参照実装との照合を加えた。未検証の全局面の正しさまでは保証しない。

## 速度の問題

前回の100ms対戦の通常探索NPS集計では、手書きに対しSFNNは平安で約1/3、
持ち駒不使用で約1/7.5だった。これは異なる対局軌跡での集計であり、厳密な同一局面ベンチではない。

コード上、`hand-category`（持ち駒不使用を含む）は `SfnnModel::apply_move` で毎回全再計算に戻る。
平安9×9は捕獲を含め差分更新する。この違いは持ち駒不使用側の追加の速度負担となる。
ただし同じ4096ノードでも1勝23敗だったため、速度改善だけで棋力問題が解消するとは言えない。

## 証跡と再現

[全216局・条件・集計・静的入力と出力・参照一致・SHA-256監査](../plans/no-hand-sfnn/20261116/)。
計測コードは `e389b0d5842f89513951ce96b90e301eecf7abd5`。後続変更はドライバーの再現・監査と文書化。
モデルハッシュ、実行ファイルハッシュは `match-conditions.json`、棋譜ハッシュは `match-summary.json`。
CPUはIntel Core i7-6700、affinity=0,1,2,3、4対局並列、native release。
ランダム序盤8手、seed=330011、最大512手、深さ上限64、Hash 16MiB。
計測中に他のビルドは実行していない。今回ブラウザー対戦・専用学習・長時間対戦は行っていない。

```sh
# 新しい保存先を使用。モデルは既存の検証済み11micro。
# ソースをcommitした同じ状態でビルド・計測する。
python3 scripts/diagnose-no-hand-sfnn.py prepare --output target/no-hand-new
taskset -c 0,1,2,3 python3 scripts/diagnose-no-hand-sfnn.py run \
  --output target/no-hand-new --model target/tuyouraou11/model

# モデル・バイナリなしで、保存された全対局の完全性・勝敗・先後ペアを再監査する。
python3 scripts/diagnose-no-hand-sfnn.py summarize \
  --output plans/no-hand-sfnn/20261116

# 静的介入の再生成（miniはモデルディレクトリを替え、末尾にminiを付ける）。
target/no-hand-new/bin/heian-probe target/tuyouraou11/model \
  < plans/no-hand-sfnn/20261116/heian-corpus.tsv
```

静的コーパスは前回の平安/持ち駒不使用比較のgameIndex=1..4の開始SFENと着手（終局の最終手を除く）。
参照照合は保存された `reference-parity.json` のSFENを順に外部参照へ渡し、
`position sfen ...` → `test nn p1ref` の出力を比較できる。
参照の構築・モデルは [既存の検証手順](tuyouraou11-sfnn.md) を使用する。

新しい診断機能は `sfnn-diagnostics` かつnative限定。製品WASMの評価・合法手・モデルを変更しない。
仮想持駒の2テスト、平安のライブラリ9件（3件ignored）、持駒ルール専用2件、
通常構成のexamples検査と変更パッケージの整形検査が成功。
持ち駒不使用のライブラリ全件実行では87成功・16失敗・4ignored。
診断機能を無効にしても同じ16件が失敗することを確認した。
持駒付きSFENや本将棋の探索点数・枝刈りを前提にした既存テストであり、今回の診断機能による新規失敗はない。
ワークスペース全体の整形検査にも既存の学習ツールの差分があるため、変更対象パッケージで確認した。
