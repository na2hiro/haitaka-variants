# 変則ルールでのつようら王評価の比較手順と #33 の結果

## #33 の比較（2026-11-05）

今回の1手100msの条件では、天王山の玉・資本還元・居玉・ひとます王でSFNNが上回り、人間将棋では手書きが上回った。王手・三枚目・命のと金は、先後ペア単位の95%区間が50%を含み、この100局だけでは優劣を断定できない。

対象は終了条件6種と玉の移動制約2種。それぞれ単独で有効化し、駒の動きを交換するdonorルールとの組合せは含めない。

ソース: `ddaf5c8`（#33のマージ後、人間将棋の「両者が全駒移動済みである必要がある」修正を適用）。製品コードの変更なし。追加したのは監査用exampleのみ。

条件: 各100局＝50序盤の先後交換。1手100ms、最大256手、ランダム序盤8手、seed=330011、8対局並列。両者とも同一ルールの同一ネイティブUSIバイナリを使用し、Aだけ `load_sfnn` でmicroモデルをロード。探索は最大深さ64、各対局で新しいセッション、標準Hash設定。モデル読込みは思考時間外。

モデル: `tuyouraou11micro-20261001-epoch0010-7f9545dbf73b-a2d18f056463`。nn.bin / progress.bin のSHA-256とサイズを照合済み。

## 同一局面の静的評価

## 検証と限界

- 各ルール固有の既存テストを実行。
- 全対局の合法手と終局勝者を監査用バイナリで再検証。採取局面ではSFNNの全再計算と差分評価が整数単位で完全一致。終局局面では手書き・SFNN両USIセッションの終局応答が一致。
- 王手将棋で全件テストを試したところ、通常将棋の継続を前提とする `play_tsume` と連続王手履歴2件が失敗した（61成功・3失敗）。全件成功とは区別し、CIと同じ王手将棋固有3件の成功を別に確認した。
- 100msのネイティブCPUでの結果。Wasm・ブラウザ、miniモデル、長い思考時間、各ルールの最適化学習モデルは未測定。引分には256手打切りを含むため、長手数ルールの優劣は慎重に扱う。

## 新しいルールで試す手順

### 1. ルールと評価器の接続を確認する

対象ルールを実装済みのブランチで作業する。合法手・王手・打ち歩詰め・終局勝者は `haitaka::Board` と探索側に任せ、手書き評価と `EvaluationStrategy::Sfnn` を切り替える。終局スコアをSFNNの静的評価で置き換えない。

SFNNに局面を渡せることと、そのルールで強いことは別に確認する。9×9盤・各側1玉・通常の駒と持駒の特徴量に収まるか、`SfnnModel::from_bytes` が当該featureを許すかを確認する。駒種・駒数・移動能力などを変えるルールでは、既存モデルの入力制約やローダーの拒否理由を確認し、拒否条件を無条件に外さない。

人間将棋のような履歴依存ルールでは、SFENから現在局面を作り直すと未移動駒の情報が失われる。初期局面と全着手をUSIの `position ... moves ...` で渡す。以下のCLIはランダム序盤も含めてこの経路を使う。

### 2. 同じfeatureのエンジン同士で対局する

モデルの取得・検証は [SFNNの説明](tuyouraou11-sfnn.md) を参照。以下はモデルが `target/tuyouraou11/model/` にある場合の例。`rule_feature` を実装済みの対象featureに変更する。居玉は `igyoku`、ひとます王は `hitomasuou`。複合ルールなら実装が対応するfeatureの組合せを指定する。

```bash
rule_feature=igyoku
model_dir="$PWD/target/tuyouraou11/model"
comparison_target="$PWD/target/tuyouraou11-rule-check/build"
run_dir="$PWD/target/tuyouraou11-rule-check/$rule_feature"
mkdir -p "$run_dir"

CARGO_TARGET_DIR="$comparison_target" cargo build --release \
  -p haitaka_cli -p haitaka_wasm \
  --bin haitaka_cli --example sfnn_usi --features "$rule_feature"
cp "$comparison_target/release/haitaka_cli" "$run_dir/cli"
cp "$comparison_target/release/examples/sfnn_usi" "$run_dir/engine"

"$run_dir/cli" self-play \
  --games 100 --threads 8 --movetime-ms 100 \
  --max-plies 256 --opening-random-plies 8 --seed 330011 \
  --a-engine "$run_dir/engine" \
  --a-engine-arg=--model-dir --a-engine-arg "$model_dir" \
  --b-engine "$run_dir/engine"
```

AがSFNN、Bが手書き評価になる。featureごとにバイナリを別の場所へコピーし、比較対象を取り違えないようにする。`--report-dir` を付けなければ棋譜・レポートファイルは出力しない。並列数は利用可能なCPUに合わせ、計測中は別のビルドや学習を走らせない。

先に対象ルール固有のテストと、少数局・短時間の対局で接続を確認する。本比較は同じ思考時間・先後交換を基本にする。固定深さでは評価器の速度差が比較に反映されない。詳細なCLI仕様は [self-play.md](self-play.md) を参照。

### 3. 結果と実装の整合を確認する

勝敗だけでなく、手数打切り・反復・時間切れフォールバックを数える。引分が多ければ上限手数、差が曖昧なら序盤数や思考時間を増やして再測定する。先後交換した2局を同じ序盤のペアとして集計する。

新しいルールでは、終局直前の局面で両評価器が同じ勝者を認識することも確かめる。差分評価に影響する局面更新を加えた場合は、`SfnnModel::apply_move` と `evaluate_from_state` の結果を `evaluate_full_refresh` と比較する。静的評価を比較するときは終局局面を除き、履歴を維持し、スコア差の小ささを棋力の証拠にしない。

## 将棋ったーで使う設定

採用するルールIDは **shogitter側**の `app/engines/enginePreparation.ts` にある `TUYOURAOU11_SUPPORTED_RULES` で管理する。この一覧は画面の選択肢とモデル読込み判定で共用される。

許可リストへの追加に加え、そのルールのfeatureを有効にしたWasmへの割当てと、モデルdescriptorの読込みも確認する。通常将棋のWasmへルールIDだけ追加すると、ルール固有の合法手・勝敗判定が反映されない。今回の比較では製品コードやこの許可リストは変更していない。
