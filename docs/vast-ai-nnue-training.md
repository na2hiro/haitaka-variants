# NNUE Training On Vast.ai

This runbook describes the current remote-GPU path for training Haitaka NNUEs
with data generated by `haitaka_learn` and PyTorch training run on a temporary
Vast.ai instance.

The 2026-08-16 Anhoku v0.5/v0.5.1 recovery, including selected hashes and Elo
results, is recorded in `docs/nnue-training-anhoku-v0.5-corrected.md`.

Use the smallest config that exercises the whole loop first. Move to a useful
model run only after data generation, transfer, CUDA setup, training, checkpoint
selection, export, download, and local verification all work for the smaller
run.

## Configs

Start by copying `haitaka_learn.toml` to a run-specific config:

```bash
cp haitaka_learn.toml haitaka_learn.my-run.toml
```

Set at least:

- `[rules].ruleset`
- `[paths].output_dir`
- `[paths].trainer_checkout`
- `[paths].bootstrap_nnue`, when using an existing `.nnue` as teacher or seed
- `[data]` game counts, sample rate, search depth, and rollout search depth
- `[training]` batch size, epoch size, worker count, max epochs, and GPU args
- `[export].output_name`
- `[selection]` checkpoint polling and self-play selection settings

Checkpoint selection defaults to a fixed-anchor ranking. Training only exports
stable, content-deduplicated candidate NNUEs; self-play starts after the GPU
trainer exits so CPU self-play cannot slow data loading. A standard reusable
configuration is:

```toml
[selection]
strategy = "anchored-ranking"
screen_games = 256
round_games = 128
max_total_games = 32768
max_games_per_candidate = 4096
explore_factor = 1.5
top_k = 3
movetime_ms = 100
storage_saver = true
```

The first unique NNUE is a fixed zero-Elo anchor, not an automatic winner.
Every other candidate receives a color-swapped paired screen; further games go
to the three largest `rating + 1.5 * standard_error` values. `ranking.json`
records pentanomial pair bins, paired Elo/CI, content hashes, aliases, and
whether selection was decisive or budget-limited. The highest point estimate
is always exported. A separate 1,024-game NNUE-vs-handcrafted report is written
for context and does not override that choice.

`--ranking-budget N` changes only the resumable ranking budget, so increasing it
does not invalidate completed matches. The legacy sequential procedure remains
available only with `strategy = "sprt"` and `--selection-max-games`.

To recover candidates and paired games produced by the old selector, keep its
`artifacts/selection/selection.json`, `candidates/`, and `matches/` together and
run:

```bash
cargo rank-existing haitaka_learn.my-run.toml \
  --ranking-budget 8192 \
  --output out/my-run/artifacts/model.reselected.nnue
```

Only complete color-swapped pairs are imported. A changed ruleset, opening,
time control, seed, or self-play binary hash gets a different match identity and
cannot silently reuse old ranking games.

For real GPU runs, include Lightning CUDA args in `[training].extra_args`.
Current Lightning versions accept:

```toml
[training]
extra_args = ["--threads", "8", "--accelerator", "gpu", "--devices", "1"]
```

If the installed trainer stack rejects those flags, use the older fallback:

```toml
[training]
extra_args = ["--threads", "8", "--gpus", "1"]
```

## Bootstrap Notes

`paths.bootstrap_nnue` has two different effects:

- During `generate-data`, Haitaka loads the `.nnue` directly and uses it as the
  teacher evaluator inside search.
- During `train`, `haitaka_learn` asks `haitaka-variant-nnue-pytorch/serialize.py` to
  convert that same file into `bootstrap.pt` and resume PyTorch training from
  it.

When `paths.bootstrap_nnue` is present, `generate-data` treats it as required
and fails if the file is missing, unreadable, or invalid. Omit the field only
when the handcrafted evaluator is intentionally the data-generation teacher.

These are different compatibility checks. A `.nnue` can be valid for Haitaka
search while failing as a PyTorch training seed.

Exported `.nnue` files are coalesced runtime artifacts. They are good for
Haitaka loading/search, and they can be useful as teachers for generating the
next dataset. They are not automatically safe as PyTorch training seeds,
especially for factorized feature sets such as `HalfKAv2^` and donor variants.

For continuation, prefer a Lightning `.ckpt` from the same run. For
cross-generation distillation, use the previous `.nnue` as the data-generation
teacher, then train from random initialization unless you know the seed can be
imported into the configured trainer feature set.

If training fails while converting `bootstrap_nnue`, keep the generated dataset
and retry with a config that removes only that field:

```bash
cp haitaka_learn.my-run.toml haitaka_learn.my-run-nobootstrap.toml
sed -i.bak '/bootstrap_nnue/d' haitaka_learn.my-run-nobootstrap.toml
rm haitaka_learn.my-run-nobootstrap.toml.bak

cargo train haitaka_learn.my-run-nobootstrap.toml
```

## Local Data Generation

Generate data locally when CPU generation is cheaper or easier than keeping the
GPU instance alive:

```bash
cargo generate haitaka_learn.my-run.toml
```

`cargo generate` reads `[rules].ruleset`, builds `haitaka_learn` in release
mode with the matching Cargo feature when needed, runs `generate-data`, and
passes extra options through.

Data generation uses all available CPU cores by default. Pass `--jobs N` only
when you need to cap CPU, memory, or thermal load.

Generation is resumable. If you stop with Ctrl-C or lose the machine, rerun the
same command; completed shard files under `datasets/shards/` are reused.

Split data generation across machines with 1-indexed shard lanes:

```bash
# Machine A
cargo generate haitaka_learn.my-run.toml --shard 1/2

# Machine B
cargo generate haitaka_learn.my-run.toml --shard 2/2
```

You can also run a contiguous range:

```bash
cargo generate haitaka_learn.my-run.toml --shard 3-5/8
```

After copying shard outputs back to one machine, merge them:

```bash
cargo merge haitaka_learn.my-run.toml \
  --input path/to/machine-a-output \
  --input path/to/machine-b-output
```

`merge-data` fails if shard manifests disagree on the git revision or config
hash. If the mismatch is expected and does not affect generated positions,
rerun with `--ignore-identity-mismatch`.

## Transfer Bundle

Create a transfer archive containing the run config, generated datasets, and the
bootstrap NNUE if the config references one:

```bash
cargo bundle-pretrain haitaka_learn.my-run.toml
```

The default archive path is
`target/pretrain-bundles/haitaka_learn.my-run.tgz`. Pass `--output <path>` when
you need a different name.

`cargo bundle-pretrain` copies the configured `output_dir/datasets` directory
and optional `paths.bootstrap_nnue`. The config inside the archive is rewritten
to use archive-local `output_dir` and `bootstrap/` paths, so unpacking into the
Haitaka checkout on Vast is enough.

## Vast.ai Instance

Vast.ai instances are Docker containers with dedicated GPU access, SSH/Jupyter
connection options, and per-second billing. Their quickstart recommends adding
an SSH key, selecting a prebuilt template, filtering offers by GPU, CPU, RAM,
network, storage, and price, and deleting the instance when finished:
<https://docs.vast.ai/guides/get-started/quickstart>.

Recommended choices for this workflow:

- Use a CUDA or PyTorch template with direct SSH.
- Use one NVIDIA GPU unless the trainer config has been tested for multiple
  devices.
- Allocate enough container disk before renting; Vast.ai notes that instance
  disk size cannot be changed later.
- Prefer on-demand for the first run. Interruptible instances are cheaper but
  can stop mid-training.
- Destroy the instance after downloading artifacts; stopping can still leave
  storage charges depending on the instance setup.

The current PyTorch install selector lists CUDA builds including CUDA 12.8 and
recommends selecting the CUDA version suited to the machine:
<https://pytorch.org/get-started/locally/>.

## Vast.ai Setup

SSH into the instance, then install system tools if the template does not
already include them:

```bash
apt update
apt install -y build-essential cmake curl git pkg-config rsync
```

Install Rust if `cargo` is missing:

```bash
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
source "$HOME/.cargo/env"
```

Clone Haitaka and the modified trainer:

```bash
cd /workspace
git clone https://github.com/na2hiro/haitaka-variants.git
git clone https://github.com/na2hiro/haitaka-variant-nnue-pytorch.git

cd /workspace/haitaka-variants
git checkout <training branch or commit>
```

Set up the trainer environment:

```bash
cd /workspace/haitaka-variants
scripts/install_trainer_requirements.sh /workspace/haitaka-variant-nnue-pytorch
```

The installer creates the trainer virtualenv, upgrades `pip`, chooses
`requirements-CUDA128.txt` automatically on CUDA 12.8+ hosts when that file is
available, and otherwise uses `requirements.txt`. Override the choice only when
needed:

```bash
HAITAKA_TRAINER_REQUIREMENTS=requirements-CUDA128.txt \
  scripts/install_trainer_requirements.sh /workspace/haitaka-variant-nnue-pytorch
```

Verify CUDA from the active virtual environment:

```bash
source /workspace/haitaka-variant-nnue-pytorch/env/bin/activate
python - <<'PY'
import torch
print(torch.__version__)
print(torch.cuda.is_available())
print(torch.cuda.get_device_name(0))
PY
```

`torch.cuda.is_available()` must print `True`.

## Upload And Train

If the Vast SSH command is:

```bash
ssh -p PORT root@HOST
```

set reusable variables on the local machine:

```bash
export VAST_HOST=HOST
export VAST_PORT=PORT
```

Then upload from the local machine with:

```bash
scp -P "$VAST_PORT" \
  target/pretrain-bundles/haitaka_learn.my-run.tgz \
  "root@$VAST_HOST:/workspace/haitaka-variants/"
```

Unpack in the Vast checkout:

```bash
cd /workspace/haitaka-variants
tar -xzf haitaka_learn.my-run.tgz
```

Run training with live checkpoint selection:

```bash
source "$HOME/.cargo/env"
source /workspace/haitaka-variant-nnue-pytorch/env/bin/activate

cd /workspace/haitaka-variants
cargo train haitaka_learn.my-run.toml
```

`cargo train` reads `[rules].ruleset`, builds the matching release
`haitaka_cli` self-play binary, then runs `haitaka_learn train-select`. During
the run it launches the trainer, watches for stable `.ckpt` files,
exports candidates, evaluates each candidate against the incumbent with
`haitaka_cli self-play`, and copies the selected model to
`[export].output_name`.

Useful overrides:

```bash
cargo train haitaka_learn.my-run.toml --selection-max-games 2048
cargo train haitaka_learn.my-run.toml --storage-saver
```

Use the explicit lower-level command only when you need to bypass the `cargo
train` wrapper and provide your own self-play binary:

```bash
cargo run -p haitaka_learn --release -- train-select \
  --config haitaka_learn.my-run.toml \
  --self-play-bin target/release/haitaka_cli
```

## Download Results

The usual handoff files are:

- the run config
- `datasets/train.json`
- `datasets/validation.json`
- `artifacts/*.nnue`
- `artifacts/export.json`
- `artifacts/verify.json`, after verification
- `artifacts/selection/selection.json`
- `haitaka-variant-nnue-pytorch` commit
- Haitaka commit recorded in dataset manifests
- Vast GPU model, VRAM, hourly price, and training duration

Lightning checkpoints under `logs/**/*.ckpt` can be large. Download them only
when you plan to resume training from that exact run.

Example download:

```bash
mkdir -p out/my-run/artifacts
mkdir -p out/my-run/datasets

rsync -avP -e "ssh -p $VAST_PORT" \
  "root@$VAST_HOST:/workspace/haitaka-variants/out/my-run/artifacts/" \
  out/my-run/artifacts/

rsync -avP -e "ssh -p $VAST_PORT" \
  "root@$VAST_HOST:/workspace/haitaka-variants/out/my-run/datasets/*.json" \
  out/my-run/datasets/
```

After confirming the files are downloaded, destroy the Vast instance to avoid
ongoing charges.

## Local Verification

After downloading artifacts into the matching local output directory, verify
that the exported NNUE loads and searches:

```bash
cargo verify haitaka_learn.my-run.toml
```

For a variant build, the wrapper commands infer features for data generation,
merge, training selection, and verification. Manual `cargo run -p haitaka_learn`
commands still need the matching feature:

```bash
cargo run -p haitaka_learn --features anhoku -- verify --config haitaka_learn.my-run.toml
```

Keep `verify.json` with the downloaded artifacts and training notes.
