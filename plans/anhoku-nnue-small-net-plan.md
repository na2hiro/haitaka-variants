# 安北NNUE：小型ネットとデータ量拡大への方針転換案

- 作成: 2026-11-23
- 状態: フェーズ0〜2完了、フェーズ3・4進行中（[フェーズ0](../docs/nnue-small-net-phase0-audit.md)、[フェーズ1〜4の記録](../docs/nnue-small-net-phase1-2.md)、2026-11-23）。過去の計画（`plans/reboot/`、`plans/anhoku-nnue-strength-first-plan.md`）の記録はそのまま残す。
- 対象ルール: 安北（`anhoku`）

## 進捗（2026-11-23）

- フェーズ1・2は完了した。2.0MBの `KingFreeA+DonorSingleEff` は、同じデータと同じ手順でHalfKA（83MB）と同じ強さになった。学習はCPUで約10分。
- フェーズ3・4は進行中。新しい生成器（`small-net-generate`）は1局面あたりの費用が旧来の約1/8〜1/11で、分布も実戦に近い。小型NNUEを教師にした第2世代では、同じ規模で+72 Eloになった。
- 現時点の最良は kf-abg1g2（359万局面）。手書き評価に対して73.8%（+180 Elo）で、現職u768との直接対局の連鎖で見ると約+170 Eloの見込みである。
- 計画からの変更点:
  - 学習は既存のGPU用学習器ではなく、CPU学習器 `scripts/small_net_train.py` で行う。GPUの賃借は不要
  - 選別は検証損失ではなく対局で行う（データを足した効果が検証損失に表れないため）
  - L1は256のまま（512にしても強くならなかった）

## 1. 結論

**今のモデルは、手元のデータ量に対して2〜3桁大きすぎる。** 原因はL1幅（256か512か）ではない。
HalfKAv2^ が「自玉の升（81通り）×駒×升」を入力にしているため、入力特徴が約15.3万行（HalfKAv2 150,903＋Donor 1,620）になっていることが原因である。
データは3万局から取った88万局面で、本将棋系で成果を出している先例（1世代あたり約1億局面）より約100倍少ない。
この組み合わせでは、どの局面でもごく一部の行しか学習されず、データの取り方や乱数シードで結果が大きくぶれる。
実際、同じレシピのモデルAとBの結果は 56.8% と 48.6% に分かれた。

次の手は、次の2点を同時に進めることである。

1. 入力を、玉位置で分けない「駒×升＋持ち駒＋DonorSingleEff」の3,483特徴に縮め、モデルを数MBにする。
2. 教師データの生成方法を変え、局面数と局数を1〜2桁増やす。

モデルを大きくするのは、データを増やしても学習曲線が伸びなくなってからにする。

## 4. 原因の診断（影響が大きい順）

1. **データ量と入力サイズの不釣り合い（主因）**
   4,086万パラメータに88万局面、つまり1パラメータあたり0.02局面しかない。
   玉位置で分けた行は、玉がよく居る十数升以外ではほとんど学習されない。
   このため、玉が動いた局面や、データの取り方で中身が変わる局面で評価がぶれる。
   早い段階で検証損失が底を打ったこと、幅を広げても伸びなかったこと、モデルAとBで結果が割れたことは、どれもこの状況の典型的な症状である。
2. **教師局面の多様性が低く、分布も実戦とずれている**
   開始局面は104通り（52の序盤×先後）しかなく、手順は深さ1の手書き探索で決めている。
   1局から約29局面を取るので、局面同士の相関も強く、局面数で見る以上に実効的な標本数は小さい。
   フェーズ0では、訓練局面の32%が80手目以降にあり、評価値の絶対値の中央値が16〜58歩分であることが分かった。
   実戦（100ms）は中央値53手で終わり、80手に届く対局は11%しかない。
   教師データの約3分の1は、実戦ではほとんど現れない「勝負のついた長い局面」である。
3. **モデルのサイズによる配布・メモリの負担**（持ち時間あたりの速さの問題ではない）
   1局ずつ指す条件では、NNUEのほうが手書き評価より速く、持ち時間あたりの損はない（フェーズ0で訂正）。
   ただし、83MBや161MBのネットはWeb配布に重く、ブラウザの1秒対局でRSSが1.85GiBまで膨らんだ。
4. **実験の回し方が遅い**
   1回の学習は数ドル・数時間で済むが、事前登録・監査・修正版の契約が積み重なった。
   R5の修正は7回改訂されたのに学習は一度も走らなかった。
   3か月で比較できた学習レシピは十数本にとどまる。
   厳密さは昇格判定にだけ使い、探索的な実験は1日に何本も回せる形にするほうがよい。

なお、`reboot`計画が直した不具合（時間切れ時の手なし負け、教師と初期値の結合、検証データの循環、引き分けの誤ラベル、量子化のシフト誤り）は修正済みなので、ここでは扱わない。

## 5. 計画

### フェーズ0：既存データでの裏付け（完了、2026-11-23）

結果は [docs/nnue-small-net-phase0-audit.md](../docs/nnue-small-net-phase0-audit.md) にまとめた。要点は次のとおり。

- 評価時に使われる特徴について、その行が訓練データに出た回数の中央値は、HalfKAで約1.2万回、玉で分けない射影で25万〜39万回だった。
  HalfKAでは、出現1,000回未満の行が評価時の特徴の17〜22%を占める。
- 訓練局面の約3分の1は、実戦ではほとんど現れない「勝負のついた長い局面」だった。
- 1局ずつ指す条件では、NNUEのほうが手書き評価より速い（NPSの損はない）。
- 成功したモデルAと失敗したモデルBは、教師局面の生成方法が違う。

### フェーズ1：小型ネット「A+Donor」の実装（3〜5日）

- 入力（片視点）は合計**3,483特徴**とする。これはフェーズ0で監査した「玉で分けない射影」そのものである。
  - 盤上の駒と持ち駒: 現行のHalfKAv2の行（1,863）から玉の升のオフセットを除いたもの。駒の種類はHalfKAv2と同じ符号化（両玉は1面を共有、金と成り駒は同じ面）で、持ち駒は枚数ごとのスロット
  - DonorSingleEff: 既存のブロック。各駒が今どの駒の動きをするかを表す。1,620
  - L1=256なら第1層は約1.8MB（int16）
- 第1層の幅は 256（第一候補）と 512（比較用）。後段の層・PSQT・層スタック・量子化・書き出しは、既存の variant-nnue-pytorch の構成をそのまま使い、変えるのは特徴集合だけにする。
- 実装箇所:
  - `haitaka_learn/trainer_overlay/` に特徴ブロックを追加する
  - `haitaka_wasm/src/nnue.rs` に新しい `FeatureFamily` を追加する
  - 既存のR1パリティ（整数参照、全再計算と差分更新、native/WASM）をそのまま使う
  - 玉が動いても全再計算は不要になる
- 初期化: PSQTを手書き評価の駒割で初期化し、学習前でも駒割評価から始める（minase方式）。
- 受け入れ条件:
  - パリティの不一致がゼロ
  - ファイルが6MB未満
  - 1局ずつの条件で、NPSが現行のL1=256のNNUE以上
- 学習環境: 3,483行 × 256 なら、MBP（MPS）や手元CPUでも学習できる見込み。GPUを借りずに回せるか、最初に1回実測する。

### フェーズ2：同じ88万局面での構造比較（1〜2日）

- A+Donor-256 と step10-u768（HalfKA-256）を、同じ訓練・検証データと同じ学習手順で比べる。
  - 同じ手順で学習曲線を取る: データの 1/8、1/4、1/2、全部 で検証損失を記録する
  - 100ms・先後交換 256組512局で手書き評価と対局する。補助として1万ノードの等ノード対局も行う
  - 教師局面の選別も比べる（フェーズ0の結果から追加）。例えば「評価値の絶対値3,000未満かつ100手未満の局面だけを使う」、あるいは「実戦の手数分布に合わせて重みを付ける」。比べるのは小型ネットで、既存の88万局面を使う
  - モデルAのコーパス（R4-replacement）とBのコーパスを、同じ小型ネットで比べ、生成方法の違いの影響を見る
- 読み方:
  - 小型ネットが u768 と同等（−2ポイント以内）以上なら、以後は小型を標準にする
  - 学習曲線が全量でもまだ下がっていれば、データが律速である証拠
  - 小型が明確に劣る場合でも、データ量を増やしたフェーズ3の10M時点で再比較してから判断する。大型ネットはデータが多いほど有利になりうるため

### フェーズ3：教師データの拡大（1〜2週間、主にCPU時間）

生成方法を次のように変える。

- **自己対局で使った探索の値をそのまま教師にする。**
  手順の決定とラベル付けを同じ探索（固定ノード）で行い、2手おき、または全手を記録する。
  ラベル用に別の探索をしなくてよくなるので、1局面あたりの費用は探索1回分になり、1局から100局面以上取れる。
- **勝負のついた局を打ち切る。** 評価値の絶対値が閾値（例えば3,000）を超えた状態が数手続いたら、その局を終える（やねうら王の `eval_limit` に当たる）。実戦にない長い大差の局面を減らせるうえ、生成費用も下がる。
- **開始局面を増やす。**
  初期局面、または既存の開始局面から、ランダムに4〜12手指して始める。
  対局の途中にも低い確率でランダムな手を入れ、その後の局面だけを記録する。
  局数は**10万局以上**を目安にする（minaseの「同じ局面数なら局数が多いほうが強い」に従う）。
- 打ち切りになった局の結果は、従来どおりWDLに使わない（λ=1.0）。

最初に、**同じCPU予算での「量か質か」**を比べる。

- A: 1万ノードで N局面
- B: 3千ノードで約3N局面（例えば 1M 対 3M）

両方を小型ネットで学習し、対局で比べる。
R3は2千ノードの教師を深い参照との一致度で不採用にしたが、それはこの段階で量と質のどちらが効くかを示す証拠にはならない。

勝った設定で 3M → 10M → 30M と増やし、各段で検証損失と対手書きの得点率を記録する。
費用の目安は、1万ノードで1,000万局面を作るのに約2,800ワーカー時間である。
これは手元8コアで約2週間、Vast.aiの64コアCPUインスタンスなら約2日・20〜40ドル程度に当たる。
3千ノードならおよそ1/3になる。
探索のNPSを上げる改善は、教師の生成費用にも対局の強さにも効く。

### フェーズ4：世代反復（フェーズ3の後）

- 小型NNUEが100msで手書き評価に明確に勝ち越したら（例: 512局で55%以上）、そのNNUEを使った探索で次の世代の教師を作り、データ量も増やす。
  これはminase・tanuki-・やねうら王が共通して使っている標準のループである。
- 過去のC/16自己蒸留が失敗したのは、「手書きより弱い教師」と「16更新」という条件のせいである。この方式そのものが否定されたわけではない。

### フェーズ5：大きくするのは最後

- 30M局面以上でも学習曲線が伸びなくなったら、初めて容量を増やす。
- 候補は小さい順に試す。
  1. 第1層の幅を512にする
  2. 進行度（駒数）による頭の切り替え
  3. 玉位置の粗いバケット（3〜9区分）
- ここでも1回の比較で変えるのは1要因だけにする。

### 昇格判定

- 既存の厳格な手順（独立データとシードでの再現、封印した開始局面、ブラウザ1秒）は、昇格候補が1つ決まった時点で1回だけ使う。
- それまでの探索的な実験では、次の記録を残せば十分とする。
  - commit
  - 設定ファイル
  - 乱数シード
  - データのハッシュ
  - 対局の生データ

## 6. 当面やらないこと

- 新しいDonor系の特徴の設計（Phase 12-A 系）。データが足りない状態では、特徴の良し悪しを判定できない。
- 88万局面のまま、HalfKA系のチェックポイント選択を詰めること。早期停止で数ポイント得をしても、データが律速である状況は変わらない。
- 161MB系のブラウザ向け最適化。
