# 第2段階: 探索用ハッシュの差分更新

状態: 採用済み（2026-11-09）。対象: 天竺大・大大・摩訶大大・泰・大局将棋。第1段階の採否記録後に着手。

## 現行と設計

`extended/large.rs::push`は毎手`Position::hash`を呼び、全マス・駒ID文字列・成り元・
状態をFNVで再計算する。moves/basic_outcome/context_keyの呼出しも調査対象。
FNVをそのままXORで差分更新できるとは仮定しない。

1. 呼出し回数と費用を再計時し、外部APIの安定ハッシュと内部キーの用途を一覧化する。
2. ルール・盤形・内部PieceId・色・位置・手番・先獅子・効果の順序を含む、固定seedの
   探索用Zobristキーを用意する。成り元の異なる内部IDを必ず区別する。
3. LargeGameにキーを保持し、差分のset・成り・全捕獲/焼却・状態変更・手番切替に対応して更新する。
   undoへ以前のキーを保存して戻す。別途「盤からの全再計算」をテスト用に実装する。
4. 内部timeline・反復判定・TTキーで全盤FNVを呼ばないようにする。
   履歴順序とpending経路によるcontextの差を維持し、異なる履歴を盤面キーだけで統合しない。
5. `positionHash`・`contextHash`等、外部に公開した既存の安定ハッシュは変更前と同一の値に保つ。
   必要時だけ旧アルゴリズムで計算する。内部ハッシュ変更とJSON仕様変更を混ぜない。
6. 手番開始時に必要な火鬼情報や凍結状態をキーへ含めるか、導出状態として扱うかを仕様に記す。
   ランダム表や追加メモリがWASM予算を超える場合は生成式・表サイズを再設計する。

## 検証

全固定局面と128以上の固定seed対局で、各完了手の適用・取り消し後に差分キー=全再計算を確認する。
成り元、複数王の消失、四天王の順序、先獅子、パス、多段移動中・再開、同じ盤面で異なる履歴を含める。
通常の千日手・連続王手・TTの文脈、保存/再読込、外部両ハッシュの互換性を確認する。
既存5ルールの全oracle比較と実WASM比較を行う。内部キーの同一性を正しさの唯一の根拠にしない。

全体の試算: 大大1.45〜1.58倍、摩訶大大1.66〜1.90倍、泰1.96〜2.40倍、大局1.85〜2.20倍。

## 実装内容

探索用キーを公開FNVから分離した。固定seedの64bitミキサーでZobristトークンを
必要時に生成するため、盤マス数×駒数の乱数表は持たない。
盤形・ルールID・内部PieceId（成り元も区別）・色・マス・手番・先獅子・
四天王の在場順序を含む。凍結・火鬼情報は盤と順序から導出され、完了手をまたぐ
独立した一時状態はない。多段移動中の制約は別途pending経路をキーへ混ぜる。

| 呼出元 | 変更前 | 変更後 |
| --- | --- | --- |
| root | 全盤FNV | 探索用キーを全盤から一度構築 |
| push | 完了手ごとに全盤FNV | Deltaの変更マスの旧値/最終値、旧/新状態と手番をXOR |
| basic_outcome | 全盤FNVで反復判定 | timeline末尾の差分キー |
| SearchGame::key | 全履歴のfoldと全盤FNV | timeline末尾の履歴順キーとpending |
| positionHash | 公開FNV | 従来通り |
| contextHash | 保存済みの各局面FNVをfold | API境界でundoから各局面FNVを復元して従来通りfold |

同じマスを何度触る経路もDeltaが最初の値を保持し、最終値との差だけを反映する。
以前のキーはundoと同じ深さのtimelineに残り、popで以前の局面・履歴順キーへ戻る。
候補列挙用にも使う全Deltaへキーを載せないため、列挙の仮適用にハッシュ計算を追加しない。
timelineは16→24 bytes/ply（+8 bytes/ply）。公開contextHashだけは一時的に
履歴分のu64配列と盤1枚を使う。履歴全体を局面キーだけにまとめない。

## 検証とperft結果

大型5ルールのextendedテストは順に51/44/45/47/48件が成功し、workspace全体も成功。
各ルールで128固定seed対局（各最大16手）と追加の長い対局（最大128手）を確認した。
全push/popにテスト専用の全盤再計算照合を入れたため、既存の焼却・全捕獲・
成り元・特殊成り・複数王・パス・多段移動・先獅子・四天王・千日手・連続王手の
固定局面も差分キーを検証する。独立に保存したFNV列から公開contextHashも照合した。

既に将棋ったーと全照合済みの同じ入力コーパスを使用した（参照実装の再実行とは区別）。
計4,482局面・457,780遷移について新Native出力は既存oracleとバイト単位で一致し、
実WASMも全合法手・全遷移・結果・公開positionHash/contextHashが一致した。
旧実WASMの親contextと、oracleの子FNVから旧履歴foldを独立に計算して全子局面を照合した。
天竺大では全子局面を旧実WASMのinspectでも直接照合した。
保存/再読込、pendingの続行・取消、Native/WASMの1000ノード探索、1ms合法フォールバック、
非対応NNUE/SFNN/USIの維持も確認した。

## FNV診断・採否

実装コミット: 0f9779989f7d03dd34a4fdcd3eb33504150a293f。

通常版NPSとは別に、ソースのコピーのFNV関数だけに計時・回数カウンタを追加した。
同一perftを3秒以上×3回実行し、葉数の一致を確認した。

| ルール | perft(N) | FNV呼出し/回・変更前 | 変更後 |
| --- | ---: | ---: | ---: |
| 天竺大将棋 | 2 | 17,491 | 0 |
| 大大将棋 | 3 | 259,508 | 0 |
| 摩訶大大将棋 | 3 | 550,221 | 0 |
| 泰将棋 | 2 | 93,285 | 0 |
| 大局将棋 | 2 | 79,600 | 0 |

公開inspectのFNV呼出しは、初期局面で4→2回、16手の履歴で36→18回。
API側のFNV計算を残すことで、公開値との互換性を維持した。
このAPI診断は回数確認であり、APIスループットのベンチマークとは区別する。

通常の数マス更新を含む固定seedの64局面で、全盤FNVに対する差分更新単体は
天竺大35.8倍・大大47.5倍・摩訶大大57.6倍・泰99.5倍・大局218.3倍だった。
これは焼却で多数マスが変わる最悪局面や、探索全体の倍率を意味しない。
計時器の追加はコンパイラの最適化や配置にも影響するため、診断の時間割合から
通常版NPSの倍率を厳密に逆算しない。採用判断には上の通常版perft実測を使う。

全対象で+10%以上、全参照とハッシュが一致し、メモリ予算も満たしたため採用。
