ルールごとに実装・検証を完結させる。名前の似た既存 `tenjiku` を天竺大将棋へ流用しない。
各ルールは取り捨て、王相当の集合による勝敗、王手放置を許す設定、ステイルメイト負けを
参照定義に合わせて使う。王相当の駒種はルールごとに異なり、通常の玉が必ずあるとは限らない。

## ルール別の特殊処理

### 天竺大将棋

`tenjikudaishogi.ts` とTenjiku系のMoveEffect/MoveFilter/ExtraMovesを対象にする。
通常の移動・捕獲・成りに加え、火鬼の周辺駒の焼却、四天王等の効果、複数移動と移動制約を扱う。
敵陣5段の成り、獅子取り規定の対象駒設定も独立して持つ。

通常捕獲・途中捕獲・成り・接触効果・手番終了時効果・勝敗の適用順を参照実装から固定する。
火鬼の配置だけでなく、効果の優先順位を決める在席順序や手番開始時の情報なども調査する。
同じ駒配置でも効果が変わる状態は、JSON・ハッシュ・復元情報へ含める。

### 大大将棋

`daidaishogi.ts` の新駒と、駒を取った際の強制成りを追加する。
全捕獲で必ず別の駒種になるとは限らないため、成り表に成り先がない駒の扱いも照合する。
複数捕獲のどこで成りを判断するか、先獅子・付け喰いの対象駒の違いを固定する。

### 摩訶大大将棋・泰将棋

`makadaidaishogi.ts` と `taishogi.ts` のMakaDaiDai方式を実装する。
捕獲を契機とする強制成りに加え、無明・法性・提婆・教王など捕獲対象によって変わる成りを扱う。
単純な「移動駒→成駒」の表だけで処理しない。王相当の駒が成る場合や、その例外も含めて照合する。
泰将棋は同じ仕組みを使い、追加された駒と王相当の集合を別に登録する。

### 大局将棋

`taikyokushogi.ts` の全使用駒・成駒を対応付け、敵陣11段の成り、獅子取り規定、
王相当の集合による終局を設定する。36×36の最終マス1295まで、省略せず扱う。
同名・似た動き・成り元の違いを確認し、駒IDや成り情報を切り詰めない。

## 状態更新と大盤の性能対策

- 1手に複数の捕獲・除去・変化が発生するため、適用と復元を対になる差分として設計する。
  駒配置、手番、効果の順序、成り、履歴、ハッシュを一緒に復元する。
- 盤面全体のコピーを探索の各枝で行う方式は大盤で負荷を測定し、差分適用・復元へ移行する。
  既存ルールのコピー方式を無条件で置き換えない。
- 固定長ワード列と有効駒の列挙を使い、全駒種×全マス対の巨大な利き表を作らない。
- 256マスでは255も有効な添字である。空マス・指し手なしのsentinelと衝突させない。
  257マス以上の添字、駒数・駒ID、置換表の経路符号化にu8の暗黙な切詰めを残さない。
- 特殊効果で王相当が複数消える場合も、完了した1手の正しい時点で勝敗を判定する。
- 探索のノード数は完了した1手の遷移を基準にしつつ、経路列挙・効果計算の途中でも
  停止要求と時間を確認する。未完了経路や不完全な局面を最善手として返さない。

## Native・WASM・将棋ったー

JSON APIに各ルールで必要な効果・継続状態を追加し、能力と仕様の版を管理する。
盤面だけの入力では正しく再開できない局面を、黙って初期状態として受理しない。
表示用の途中操作と、検索する完了した1手の対応を各ルールで確認する。

まず手作り評価で合法なAI対局を成立させる。駒の価値と効果をルールごとに設定し、
既存NNUE/SFNNや本将棋用の詰み・王手枝刈りを適用しない。
WASMの初期化時間、モジュールサイズ、実メモリ、時間制限下の応手を計測する。

## 検証と完了条件

- 各特殊効果を単独で検証してから、複数の効果・捕獲・成りが同時に起こる固定局面を比較する。
- 天竺大将棋では火鬼・四天王の接触と順序、移動継続・終了、王相当の除去を重点検証する。
- 大大・摩訶大大・泰将棋では捕獲による成り、対象に依存する成り、非成駒と例外を検証する。
- 全使用駒の移動・成りを覆う駒別fixture一覧を作り、未検証の駒が残っていれば完了にしない。
- 255/256、各サイズの最終マス、1295、最終ワードのpaddingを確認する。
- 差分適用・復元、最初からの再生、JSON往復、ハッシュ全再計算が一致することを確認する。
  同じ駒配置で効果順序が異なる局面の非同一性も確認する。
- 固定特殊局面と各128局面以上で、完了した1手・全効果・結果を参照実装と比較する。
- 実WASMとブラウザで初期・途中・特殊効果直前の局面から対局し、再開・待った・終局を確認する。
- 全14ルールの対応表、仕様版、再ビルド手順、検証記録を更新する。各ルールの完了コミットを記録する。

応答が返るだけでは完了としない。駒の対応・状態遷移・終局に不一致がなく、時間切れでも
合法な完了済みの手を返せることを必要条件とする。強さの評価・学習・初心者向け調整は別作業。

### 天竺大将棋の仕様固定

- 66種類の駒・成駒、初期156枚。四天王の在席順序と先獅子を完了局面の状態へ含める。
- 火鬼・副将の三回歩行は捕獲で停止する。四天王の隣接捕獲は元のマスへの帰還が必須。
- 成りは五段のNormal方式で、多段移動中の成り可否を蓄積し、終了時またはパス時に成る。
- 将の跳越しは、参照の`jumpException`に列挙された駒の手前で止まり、その駒には着地しない。
- 凍結は移動開始時の制約。途中で四天王に接しても移動は続けられる。
- 手番開始時に有効だった敵火鬼を優先して到着駒を焼き、その後、凍結していない火鬼の焼却を同時適用する。
  捕獲済みの火鬼を同じマスの到着火鬼と取り違える参照実装の不具合は、説明と回帰テストに合わせて修正した。
- 最後の王相当を継続移動の途中で通常捕獲した場合は、その時点で終局し、手番終了時効果を追加しない。
- 双方の王相当が焼却で消えれば引き分け。ステイルメイト負けは参照どおり、王手が掛かっていない場合に限る。
- JSON v4は最長三段の経路と、完了局面＋一段目・二段目までの`pending.path`を扱う。
  途中局面の手番開始時の火鬼情報は参照の保存データと照合し、欠落した途中状態を黙って受け入れない。

## 大大将棋の着手（2026-11-08）

ブランチは`feat/dai-dai-stage5`、将棋ったー側は`feat/haitaka-dai-dai-stage5`。
前ルールと同じWASM初期化5秒、線形メモリ64MiB、対局思考5秒を予算とし、1ms制限も確認する。
既存の http://localhost:3002 を使用する。

採用仕様:

- 17×17・5ワードのビット盤、添字u16、85駒ID・64元駒（21種に成り先）・初期192枚（片側96枚）。
- 捕獲があれば成り先のある駒は必ず成る。成り先のない駒はそのまま。静かな移動では成らない。
- 多段移動では捕獲による成り可否を保持し、完了・パス時に成る。継続中の王捕獲では、成りの前に終局する。
- 天狗・鉤行の走りは、空きマスで直角に一度曲がれる。曲がる地点では捕獲できず、終点だけで捕獲する。
  将棋ったーのtype102に合わせて、一段の原子的な移動として扱う。
- 狛犬は同一直線上の三回移動と帰還を持つ。飛び越しには参照の`mustNotBeEmpty`で指定された味方駒が必要。
  方向別の定義に相違があっても、一般論で補正せず参照の座標条件を採用する。
- 獅子取り規定の対象は`bl`と`dh`。奮迅・狛犬は獅子と同じ扱いにはしない。付け喰いに歩は使えない。
- Capture方式では行き所のない未成駒も残れる（成り表のない歩・香など）。JSONの復元もこれを許容する。
- JSON v4を継続使用し、ルールID60を明示する。`shitenno`は必ず空で、先獅子は履歴とハッシュに含める。
- 全85駒の先後別・空盤と捕獲周辺配置、3回捕獲・強制成り・途中再開・17筋を固定局面で覆い、
  128ランダム局面と全完了手遷移、実WASM・ブラウザを検証してから完了にする。
