## 目的と合意した進め方

その基盤を使って、将棋ったーの「古将棋」カテゴリ全14ルールへ広げる。
最初の到達点は、平安将棋3種の合法手・勝敗判定・基本的な探索・Native/WASM・
将棋ったー上のAI対局である。初心者向け棋力調整は
[別計画](../beginner-bot-strength-control.md)で扱う。

今回の作業は本ロードマップと段階別計画の保存のみ。エンジン実装やコミットは含めない。
各段階は依存する段階の完了条件を満たしてから着手し、実装開始時に本計画を更新する。

## ルールの基準と参照元

歴史的ルールには異説があるため、採用仕様は将棋ったーの実装に合わせる。
ルール名だけから一般的な規則を推定しない。初期配置、駒定義、継承された既定値、
成り、捕獲、手番の継続、勝敗、千日手を含む解決済みの仕様を確認する。

## 共通の実装方針

- 1パッケージ1ルールのコンパイル時選択を維持する。本将棋の高速な座標・Magic経路を
  温存し、新しい汎用処理を既存ルールのホットパスへ無条件に入れない。
- [既存の大盤用固定長ビット盤](../../docs/minishogi.md)は基盤として再利用する。
  現在の `Board` がそのまま36×36で動くという意味ではない。
- 盤の形、ビット盤の容量、駒種、捕獲・成り・終局の規則を分離する。
- 王手回避・唯一の王・駒14種類・持ち駒7種類・2座標だけの指し手という前提を、
  必要な段階で順に外す。合法性を変える状態は保存・復元・ハッシュに含める。
- NativeとWASMで同じルール処理を使う。新ルールではまず手作り評価を使い、
  既存NNUE/SFNNの誤読込を防ぐ。学習モデルの作成・棋力保証は後続作業とする。
- 単なる盤面一致ではなく、完了した1手の合法手・遷移後の状態・終局を参照実装と比較する。
- 未対応ルールや未対応の局面状態は明示的に拒否し、近い別ルールとして探索しない。

## 共通の検証と進捗管理

各段階の完了には、ルール別の固定テスト、参照実装との比較、Native/WASMの一致、
将棋ったー上の対局が必要。複雑な特殊効果は、ランダム対局だけでなく固定局面で検証する。

検証記録には参照コミット、ルール仕様の版、局面・履歴、seed、探索条件、実行環境、
不一致と解消理由を残す。既存ルールの回帰テストと本将棋の性能比較も行う。
各段階の状態を「未着手 → 実装中 → 検証中 → 完了」と更新し、完了コミットと証拠を記録する。

Fairy-Stockfishは実現可能なルールの独立比較と設計の参考に使う。公式FAQの盤サイズ上限は
12×10であり、中将棋以降の検証を同エンジンだけに依存しない。
