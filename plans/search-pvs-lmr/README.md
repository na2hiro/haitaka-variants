# 探索の PVS・1 ply LMR 実験

PVS（Principal Variation Search）と 1 ply の LMR（Late Move Reductions）を、既定オフの Cargo feature として実装した。
2026-11-21〜25 に、本将棋、変則5ルール、中将棋（手作り評価と Minase NNUE）で対局を計測した。

**現時点で、棋力の向上は確認されていない。** 95%信頼区間が0を外れた比較は25件中4件ある。
そのうち2件は持ち時間によって向きが逆になった。残り2件も1回だけの計測なので、追試の候補として扱う。
既定ビルドの探索は変えていない。

## 有効にする方法

| 対象 | PVS | PVS＋LMR |
|---|---|---|
| 本将棋（`haitaka_wasm` の共通探索） | `search-pvs` | `search-lmr` |
| 変則ルール（共通探索・JSON 系） | `search-variant-experiments,search-pvs` | `search-variant-experiments,search-lmr` |

- `search-lmr` を付けると `search-pvs` も有効になる。`haitaka_cli` は同名の feature を転送する。
- 本将棋で PVS・LMR が働くのは、変則ルールの feature を何も付けていないビルドだけ。
- JSON 系の LMR は、静かな手を判定できるルールだけで使う（小将棋、中将棋、v3 のうち王手放置禁止で獅子の二段手、トライ、強制捕獲がないルール。通常系ルールの多くもこれに当たる）。大型の v4・v5 は PVS だけを使う。詳しくは [中将棋のドキュメント](../../docs/chushogi.md#json-系の探索実験)。
- WASM の `search_json`（`haitaka-json-v2`）の入出力は変えていない。試し読みや短縮の件数は JSON には出さず、USI の `info` にだけ出す。

## 判定の一覧

各行は「A 対 B」で、ペア Elo は A から見た値。区間は先後ペアの得点を標本にした95%信頼区間。

### 比較の数についての注意

上の表にある比較は25件（打ち切りが多い比較を含む）。95%信頼区間では、効果がまったくなくても1件程度は偶然0を外れる。
区間が0を外れた4件にも、偶然の可能性が残る。
既定でオンにするかどうかは、事前に決めた基準による追試で決める。

## 次の手順

1. 本将棋の PVS＋LMR 対 PVS（1手1秒）を SPRT で追試する。基準とする Elo の幅は追試の前に決める。
2. 5五将棋の PVS＋LMR 対 PVS を、局数を増やして追試する。
3. 中将棋は1局が長く、32局でも区間が ±60〜140 Elo ある。1手1秒で局数を増やすか、持ち時間を短くして局数を確保するかを決めてから測る。
4. 枝刈りありで Minase v3 と v2.6 を比べる場合は、両側とも PVS＋LMR にして直接対局させる。今回の3比較を足し合わせても推定できない。

## 移植後の照合

計測したコードは2系統ある。本将棋・変則ルール・中将棋（手作り評価）は `feat/handcrafted-eval-experiments`（`7f29506`）に載せた未コミットの実装で、Minase NNUE は main `8630a75` に [`experiment.patch`](receipts/chu-minase/experiment.patch) を当てたもの。
このブランチでは、どちらも最新 main（`1c87fe3`）に載せ替えた。載せ替えた後の release ビルドで、次の点を確かめた。照合結果は [`receipts/regression/regression.json`](receipts/regression/regression.json)、テストの一覧は [`tests.txt`](receipts/regression/tests.txt)。

| 照合 | 条件 | 結果 |
|---|---|---|
| 本将棋・既定ビルド 対 main | 固定7局面と開始局面の `go depth 4/5`、開始局面と千日手直前局面の `go nodes 1/128/30000` | 22/22 で `bestmove` と `info` が一致 |
| 本将棋・PVS 対 計測時の PVS バイナリ | 同上 | 22/22 一致 |
| 本将棋・PVS＋LMR 対 計測時の LMR バイナリ | 同上 | 22/22 一致 |
| 中将棋・手作り評価・既定ビルド 対 main | 将棋ったー参照局面242件 × ノード予算 1/128/1000、深さ8 | 726/726 で `haitaka-json-v2` の出力が一致（時間と NPS を除く） |
| 通常系ルール・既定ビルド 対 main | どうぶつしょうぎ（トライ）、取る一手（強制捕獲）、獅子王（獅子）、八方桂・ざりかに（王手放置あり）、不成。開始局面から合法手を決まった順に選んだ局面 × ノード予算 1/128/1000、深さ8 | 計186件で JSON 出力が一致（時間と NPS を除く） |
| 中将棋・Minase NNUE（基準・PVS・PVS＋LMR） 対 計測時の固定深さ | 10局面 × 深さ3・4 × v3・v2.6 × 3構成 | 120/120 でスコア・選択手・ノード数・完了深さ・終局が一致 |
| 中将棋・WASM（既定） | 将棋ったー参照局面242件・16,121遷移 | ネイティブの参照出力と一致 |

テストは、本将棋の既定・PVS・PVS＋LMR、安南、NekoNeko、5五将棋、平安将棋（9×9）、持ち駒不使用、王手将棋の各構成（`haitaka_wasm`）と、小将棋、中将棋、京都将棋、天竺大将棋、大局将棋、上の通常系6ルール（`haitaka`）で実行し、すべて通った。
中将棋の CLI・USI と Minase モデルのテストも実行した。

通常系の28ルールは、`search-pvs` と `search-lmr` のどちらでもコンパイルできることを確かめた。LMR の対象になるルールも含め、通常系ルールでの対局は計測していない。

main の時点で次のテストと照合が通らなかったため、このブランチで直した。

- 5五将棋と平安将棋の `haitaka_wasm` テストがコンパイルできなかった。`0fadfc3` で `parse_usi_position_with_history` が `parse_usi_position_with_limit` に置き換わったのに合わせた。
- 持ち駒不使用と王手将棋の `haitaka_wasm` テストが、それぞれ16件と6件失敗していた。持ち駒のある局面や王手の回避を前提にした本将棋向けのテストなので、既存のテストと同じく、そのルールのビルドでは除外した。
- `scripts/verify-chushogi.mjs` は、中将棋の WASM が NNUE を読み込めないことを前提にしていた。Minase に対応した main では16行目で止まっていたため、空のファイルが不正な形式として拒否されることを確かめるように変えた。
