# 小型NNUEを性能変化系以外へ広げる計画（5五系から）

- 作成: 2026-11-28
- 状態: 計画（未着手）
- 前提: 性能変化系12ルールの小型NNUE（KingFreeA+Donor、L1=256）は、どれも手書き評価に +270〜+502 Elo 勝った（[学習記録](../docs/nnue-small-net-results.md)）。同じ手順を、ほかのルールにも使えるようにする。

## 1. 結論

1. **最初は、5五系のうち普通の駒で指す5ルールにする。** 5五将棋（51）、ジャドケンス（52）、ゴロゴロ（96）、ゴロゴロ＋（97）、5五金銀（110）の5つである。どれも 9×9 と同じ `Board` で動いている。学習用の `haitaka_learn` は、手を入れなくても5五用にビルドでき、自己対局による生成も動いた。足りないのは次の3つだけである。
   - 小さい盤用の入力（特徴集合）
   - 学習データの形式
   - 小さい盤での NNUE の読み込み
2. **ネットは約0.6MBになる。** 盤が 25〜36マスなので、入力は約820〜1,040行になる（9×9 は 3,564行）。生成も速いので、1ルールが数時間〜半日で終わる見込みである。
3. **反転する4ルールは後回しにする。** 京都、金桂舞、マイクロ、京都vs5五である。これらは別のエンジン（JSON v3、`Board` を使わない）で動いていて、NNUE を使う仕組みそのものがない。
4. **5五系の次は、9×9 の勝ち方・玉の制約が違うルールにする。** 王手将棋、三枚目、命のと金などである。盤もエンジンも既存のままで、Donor ブロックを外すだけで済む。ただし比べる相手は、手書き評価ではなく、いま将棋ったーで使っている評価（本将棋用の SFNN）になる。

## 2. 調べた事実（2026-11-28）

| 項目 | 結果 |
|---|---|
| `haitaka_learn` の5五ビルド | `cargo build -p haitaka_learn --features haitaka/minishogi,haitaka_wasm/minishogi` が通る |
| 生成 | `small-net-generate` が5五で動く。16局、2,000ノード/手で400局面を0.4秒で作った。ただし記録の `rule` が `"standard"` になっている（直す） |
| 特徴の書き出し | `small-net-export-features` は「this build's donor rule has no KingFreeA family」で止まる |
| NNUE の実行側（`haitaka_wasm/src/nnue.rs`） | 盤の升の数が `SQUARES = 81` で固定されている。小盤では `NnueModel::from_bytes` がすべてのネットを拒否する（`ALLOW_STANDARD_MODELS = false`） |
| 学習データ（64バイト） | 9×9 の座標で固定。5×5 の局面は 9×9 の隅に埋め込めば書ける。ただし、読み戻すと 9×9 の SFEN になるので、小盤の `Board` に戻せない |
| レイヤースタックの選び方 | 盤上の駒の数で8つに分ける。上限が40枚なので、5五（12枚）では0〜2番しか使わない |
| 学習器（`scripts/small_net_train.py`） | 行数が `BASE=1944`、`DONOR=1620` で固定されている |
| 手書き探索の速さ（このPC） | 5五の初期局面で、100ms に深さ6、41,000ノード（約40万ノード/秒） |
| 将棋ったー | 5ルールとも、評価は手書きだけ（`haitakaEngineConfig.json` の項目が空） |
| 外部の強さの物差し | Fairy-Stockfish（5五・ジャドケンス・ゴロゴロに対応）はどのマシンにも入っていない。`self-play` は外部 USI エンジンと対局できる |

## 3. 入力（特徴集合）

KingFreeA を、盤の大きさに合わせて作り直す。9×9 版と同じく、次の行で構成する。

- 駒の種類×升（先手・後手。玉は両者で1面を共有する）
- 持ち駒の枚数
- 敵玉の升（両方の玉を見分けるため）

| ルール | 盤 | 升 | 行数 | ネットの大きさ（L1=256） |
|---|---|---:|---:|---:|
| 5五、5五金銀 | 5×5 | 25 | 824 | 約0.6MB |
| ゴロゴロ、ゴロゴロ＋ | 5×6 | 30 | 924 | 約0.7MB |
| ジャドケンス | 6×6 | 36 | 1,044 | 約0.75MB |

- **駒の種類**は 9×9 と同じ10種類にする。成った小駒は金として扱う。5五にない香・桂の行は、使われないだけで害はない。
- **持ち駒**も 9×9 と同じく、駒の種類ごとに18枚分の行を持たせる。使わない行のぶん約0.17MB大きくなるが、学習器をそのまま使える。必要になったら、あとで削る。
- **レイヤースタック**は、駒の数の上限をルールごとに変えて、8つとも使えるようにする。上限は、5五が12枚、5五金銀が16枚、ジャドケンスが14枚、ゴロゴロが16枚、ゴロゴロ＋が20枚である。
- **ネットの見出し**には、ルールごとに違うハッシュを入れる。中に、盤の大きさとルールの番号を含める。別のルールのネットは読み込めない（性能変化系と同じ）。
- **L1** は256のままにする。性能変化系と同じ WASM の機能（`nnue-l1-256`）、同じ学習の手順が使える。

## 4. 進め方

### フェーズ0：エンジンと学習器を小盤に対応させる（このPC、1〜2日）

1. `nnue.rs` で、升の数、持ち駒の行、駒の数の上限を、選んだ盤から決める。そのうえで、小盤の KingFreeA を作る。
2. 小盤用の KingFreeA のネットだけは、`from_bytes` で読み込めるようにする。9×9 のネットは、今までどおり拒否する。
3. 学習データの書き出しと読み戻しを、小盤でも往復できるようにする。9×9 の座標に埋め込む形を使い、生成したデータ全件で往復を確かめる。
4. 生成の記録のルール名を、ビルドしたルールにする。
5. 学習器の行数を、書き出し側が出すメタデータから読むようにする。`--rule minishogi` などを足す。
6. 差分計算の確認を足す。手を指しながら差分で更新した値と、最初から計算し直した値が、ランダムな対局で一致することを確かめる（9×9 にある確認を広げる）。
7. 5五用の WASM（普通版と SIMD 版）をビルドし、ネットを読み込んで探索できることを確かめる。

**合格の条件**: 10万局面で学習した試作のネットが、CLI でも WASM でも読み込める。合法手だけで対局を最後まで指せる。差分計算と計算し直しが全局面で一致する。9×9 の既存のテストも通る。

### フェーズ1：5五で試す（mbp で生成・学習、mba で対局。半日）

- **1手のノード数**: 5五は1手が軽いので、10,000ノード/手でも約25msである。データの量と時間は、第1世代で決める。100万局面と300万局面を比べて、対 手書きの対局で選ぶ（性能変化系で、検証損失では選べないとわかっているため）。
- **開始局面の多様性**: 5×5 では、初めの数手をランダムに指しても同じ局面が多く出る。生成の開始局面と、評価対局の256組の開始局面について、重複の割合を測る。多ければ、ランダムな手を増やすか、重複を除いた開始局面の集合を作る。
- **千日手と連続王手**: 将棋ったーの規則（4回の繰り返しは引き分け、連続王手をかけた側の負け）どおりに、生成で終局しているかを確かめる。
- **進める条件**: kf1 が手書き評価に勝つこと（95%信頼区間の下限が0より上）。満たせば、性能変化系と同じく kf4 まで進める。kf1 の差が +100 に届かなければ、データの量とノード数を見直してから進める。

### フェーズ2：残りの4ルール（mbp の2列で並べて回す。1日程度）

ジャドケンス、ゴロゴロ、ゴロゴロ＋、5五金銀を、フェーズ1で決めた設定で回す。ゴロゴロ＋と5五金銀は最初から持ち駒があるので、持ち駒の行がよく効くはずである。

### フェーズ3：将棋ったーに入れる

- 性能変化系と同じ自動の反映（対局を見張るランナー、`integrate_rule.sh`、バージョンの付け方 `v1.<世代>`）を、少し直して使う。
- バージョンの「形式」はルールごとに数える。5五の最初の形式も `1` にする。
- ブラウザテスト（`tests/haitaka-variant-nnue.spec.ts`）は対象のルールを設定から読むので、5ルールは自動でテストに加わる。

### フェーズ4以降：次の種類のルール

| 順 | ルール | 必要な作業 | 比べる相手 |
|---|---|---|---|
| 4 | 9×9 の勝ち方・玉の制約が違うルール（王手、三枚目、命のと金、四本歓喜、人間将棋、天王山の玉、居玉、一升王） | KingFreeA（1,944行）から Donor を外したものを、各ルール用にビルドする。人間将棋の「まだ動いていない駒」は入力にないので、あとで面を足すことを検討する | 将棋ったーで今使っている評価（本将棋用の SFNN） |
| 5 | 持ち駒の扱いが違うルール（仲間割れ、伏兵、共有、バ抜き、点数、スイカ） | ルールごとに [hand-rules.md](../docs/hand-rules.md) の NNUE 対応を確かめる。増殖は持ち駒が18枚を超えるので対象外 | 同上 |
| 6 | 反転する5五系4ルール、古将棋（平安、小、中、鳥、和、大 など） | JSON 側のエンジンに NNUE の入口、学習データ形式、生成器を新しく作る。別の設計が必要 | 手書き評価 |

手数将棋は、指した手数が状態に入っていて、学習も無効にしているので、対象外とする。

## 6. 決めてほしいこと

1. **PR の分け方**: 5五系は新しい PR にする（haitaka-variants と将棋ったーにそれぞれ1つ）か、今の #50 と #949 に足すか。**新しい PR を勧める。** 今の2つはすでに大きく、変更の中身（小盤への対応）も違うためである。
2. **Fairy-Stockfish を物差しに使うか**: mba にソースからビルドし、5五・ジャドケンス・ゴロゴロで外部の強いエンジンと比べる。オープンソースで無料だが、GitHub からの取得が必要である。千日手の規則が将棋ったーと違う（5五では千日手が先手の負け）ので、その局は Haitaka 側の規則で判定し直す。使わなくても、手書き評価との比較で計画は進められる。

## 7. 気をつけること

- 小さい盤では手書きの探索でも深く読めるので、評価の差が出にくいかもしれない。kf1 の結果を見て判断する。
- 成った小駒を金として扱うので、取られて持ち駒に戻ったときの違いは入力に出ない。ただし、これは 9×9 と同じ扱いで、5五では成銀もと金も金と同じ動きをする。
- 小盤の各ルールは別々のビルドになる（1つのエンジンに複数の小盤ルールを入れられない）。WASM もルールごとに作る。
